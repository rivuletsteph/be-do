# `skills`

**When:** the weekly close, after the fold; after any pull request that adds or changes a skill; and whenever she asks whether her skills are up to date

**Command:** `skills`

Her concern, 12 Nov 2026: installed skills need to stay in step with the repo. That day one skill was installed and nowhere in the repo, and three still carried their whole text beside a repo copy that had moved on.

It reads the installed skills on this machine and the list of skills the version store holds, and sorts each of be•do's own into a state:

- **loader**: it downloads its procedure each run. Always in step.
- **older copy**: the repo holds the skill, but the installed one carries its own text. The repo wins (25 Oct 2026). The line names the loader file to install in its place, or says there is none yet: write one by pull request first.
- **installed only**: be•do's, and nowhere in the repo, so it is never tested, never checked for privacy, and changed only by upload. Each is a backlog item: move the procedure into the repo with her specifics in a settings row, never in the file, then install its loader.
- **in the repo, not installed here**: said in one line, never a fault.

`all in step` means nothing to do. Otherwise give her the list once, shortest first, as one yes: installing or replacing a skill is hers (J14), so be•do names the file and she installs it. It changes nothing itself.

It finds installed skills in the usual folders; pass `--installed FOLDER` where they live somewhere else. A chat that can't see the installed skills says so in one line.
